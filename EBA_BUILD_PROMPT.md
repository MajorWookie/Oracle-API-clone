# EBA Build Directive: The Enterprise Suite — Plan, Then Build

*Addressed to the LLM behind Enterprise Business Applications (EBA).*

---

## 1. What this document is

You are the builder of Enterprise Business Applications — a modern, unified suite of enterprise software: sales, quoting and pricing, orders and fulfillment, inventory, manufacturing, procurement, financials, projects, people, and service, on one platform. This document is the product of a deep analysis of the complete API surface of Oracle's enterprise estate — Oracle Fusion (Supply Chain, CX Sales, Financials, HCM, Procurement, Projects, and common services) and Oracle CPQ — comprising roughly 33,000 documented operations across more than 1,100 API collections. That analysis extracted what applications of this class actually let people and systems do: the full functional surface of a top-tier enterprise suite.

Treat everything here the way the analysis treated Oracle: as **evidence of required capability, never as a design to copy**. Oracle tells us *what* an enterprise suite must do. It frequently also demonstrates *how not to do it*. You are building a product, not a mimic.

Your job, in order:

1. **Plan.** Produce a build plan before writing any code (Section 3 defines what the plan must contain).
2. **Execute.** Build the next stage of EBA against that plan — application capability, Supabase data model, and EBA's own REST API advancing together as one coherent model.

## 2. The Prime Directive

Learn the breadth from Oracle. Design decidedly better. Concretely:

- Where Oracle offers ten inconsistent doors into one room, EBA builds one well-made door.
- Where Oracle's model reflects thirty years of acquisitions — five separate REST dialects, duplicated resources, UI metadata leaking into transactional APIs — EBA has one dialect, one resource per business concept, and clean separation of concerns.
- Where Oracle is genuinely deep — effective-dated employment records, configurable products with constraint rules, multi-step fulfillment orchestration, holds, returns, revenue lines, subledger flows — EBA matches the depth. Depth is not the thing being simplified. **Ceremony is.**

Every domain in this document expresses capability at three layers, and the three must be one model, not three:

1. **In-app** — what a user can see and do in the application.
2. **In-database** — the Supabase (Postgres) schema that stores it.
3. **Over REST** — EBA's API, exposing the same model to systems.

A capability that exists in the app but not the API, or a table shaped differently from the resource above it, is a defect.

## 3. Plan first: what your plan must contain

Before building, produce a written build plan covering:

- **Stage map.** Order the domains by dependency and deliver in stages. The dependency spine, learned from how Oracle's domains actually reference each other: platform foundation → parties → catalog & items → pricing → the transactional domains (quoting, orders, procurement, inventory, projects, people, financials operate in parallel once their masters exist) → cross-domain flows (quote-to-order, order-to-invoice, procure-to-pay, hire-to-pay). Justify any deviation.
- **Per-stage scope.** For each stage: the capabilities shipped, the tables created or migrated, the API resources exposed with their methods, and the documentation artifacts updated.
- **The seams.** Name the cross-domain contracts (which domain owns parties, how orders reference items, how everything posts to the ledger) before building either side of any seam.
- **Verification per stage.** How you will demonstrate each stage works: seeded demo data, API-level tests for every operation, and at least one end-to-end flow exercised per stage.

Then execute stage by stage. Do not build all domains shallowly at once; make each stage genuinely usable.

## 4. Universal design principles — EBA's constitution

These principles were derived by contrast with observed Oracle behavior. They apply to every domain, every table, every endpoint, with no per-module exceptions. Oracle's estate is the cautionary tale for each one.

### 4.1 One dialect
Oracle splits its estate across at least five REST gateways with different conventions — separate SCM/CRM/HCM API roots, a differently-versioned CPQ dialect, and satellite products with their own idioms; even parameter casing disagrees (`orderBy` in Fusion, `orderby` in CPQ). EBA exposes **one API root, one version scheme, one convention set**. A developer who learns one EBA resource has learned them all.

### 4.2 One resource per business concept
Oracle ships parallel resources for the same object — a sales order surface for the "Order Hub" alongside the general sales order surface; separate self-service ("My …") copies of administrative resources; buyer-side and supplier-side duplicates of the same document. EBA models each business concept **once**, and uses authorization scope — Postgres row-level security and role-based field visibility — to shape what each audience sees. A view is a permission, not a second resource.

### 4.3 One query language
Oracle's better-behaved families converge on a usable pattern: filterable collections (`q`), field selection (`fields`), relationship expansion (`expand`), sorting, and offset pagination with totals. EBA adopts the good idea and standardizes it everywhere:

- `filter` — one documented expression syntax, same operators on every collection.
- `fields` — sparse field selection.
- `expand` — named relationship expansion, bounded depth.
- `sort` — `field` / `-field`, multi-key.
- `limit`/`offset` with `totalResults` on request; cursor pagination on collections expected to grow unboundedly (event logs, transactions).
- Saved/named queries where users need reusable filters — one mechanism, suite-wide.

### 4.4 Full method coverage, applied with judgment
Every resource supports the full REST method set where the semantics genuinely exist: GET (collection and item), POST (create), PATCH (partial update — the default write), PUT (full replace, only where a resource is a true document), DELETE (with explicit semantics — see 4.6), HEAD (existence/metadata probes), OPTIONS (capability discovery). Method support is a per-resource design decision, not boilerplate: a posted financial document does not accept DELETE; a reference-data row does.

### 4.5 Identity: business keys outward, surrogate keys inward
Oracle URLs mix human-meaningful keys (order numbers) with opaque composite hashes (`UniqID` values) unpredictably. EBA: every table has a UUID primary key internally; every resource is addressed externally by its **stable business identifier** (order number, item number, invoice number, email-unique username) when one naturally exists, else by UUID. Never both, never composite hashes in URLs.

### 4.6 State is data; actions are rare and explicit
Oracle scatters hundreds of POST `action/` verbs per family — including thousands of per-resource duplicates of the same generic UI actions. EBA:

- Simple transitions are `PATCH` on a `status` field, validated by the state machine in the database and service layer.
- Genuinely procedural operations — submit for approval, release a hold, split a shipment line, run an allocation — are explicit, documented `POST /{resource}/{id}/actions/{verb}` endpoints, **only** where a PATCH would hide real side effects.
- Documents that must survive for audit (orders, invoices, journals) are cancelled or reversed via status/action — never DELETEd. Drafts and reference data delete normally.
- UI affordances (which buttons a user sees) are the application's concern, computed from state and permissions — they are **not** API resources. Oracle's thousands of "smart action" endpoints are the anti-pattern.

### 4.7 Consistent shape
- Resource names: plural nouns, kebab-case path segments, camelCase JSON fields, snake_case tables — one casing rule per layer, no exceptions.
- Nesting expresses composition only (`/orders/{orderNumber}/lines`), one or two levels; anything deeper gets promoted to a top-level resource with a filter. No `/child/` markers.
- One flat namespace: every resource name is unambiguous across the whole suite. Where two domains would claim the same noun (employment assignments vs project staffing assignments; purchase requisitions vs job requisitions; background jobs vs job definitions vs job postings), your plan assigns each a distinct, self-explanatory name before either is built.
- Every record carries who-columns (`created_at`, `created_by`, `updated_at`, `updated_by`); every response carries them uniformly.
- One error envelope suite-wide: machine-readable code, human message, field-level details, correlation id.
- Optimistic concurrency via ETag/`If-Match` on writes; idempotency keys accepted on POST for safe retries.
- One batch mechanism suite-wide (uniform envelope for many-item create/update), not per-product inventions.

### 4.8 The platform is built once
Attachments, notes, custom fields, lookups/reference data, audit history, saved searches, background jobs, notifications, and full-text search are **shared platform services** with one implementation and one API shape, attached to any resource by convention (`/{resource}/{id}/attachments`, etc.). Oracle re-implements or re-exposes these per family; EBA does not. Custom/extension fields are a governed registry over JSONB columns — no flexfield ceremony.

### 4.9 Time is modeled honestly
Where history matters — employment records, price lists, rates, territory definitions — records are effective-dated (`effective_from`/`effective_to`) with a defined way to query "as of" a date. Where only the present matters, they are not. Choose deliberately per entity; document the choice.

### 4.10 Introspection
EBA's API is self-describing: OPTIONS and a `/describe`-style metadata endpoint expose each resource's fields, types, and supported operations — generated from the schema, never hand-maintained. (This is one Oracle idea worth keeping — standardized, not per-dialect.)

## 5. The domains: capability, data, and API — one model per domain

Each section below is a build directive for one functional domain: what the application must let people do, what the Supabase schema must hold, and what the REST surface must expose. The capability lists are distilled from the full Oracle surface — treat them as the floor, not the ceiling. Where a note says "Oracle splits/duplicates X," that is a warning label: EBA builds it once.

Sequence dependencies are explicit: 5.1 (platform) and 5.2 (parties) come first; 5.3–5.4 (catalog, pricing) before any transactional domain that sells or buys; the rest can proceed in parallel per your plan.

### 5.1 Platform foundation (build first — everything else mounts on this)

Oracle re-implements these primitives in every product family, in up to four dialects each (lookups alone ship as four resource families across three API generations). EBA builds each **exactly once**, as a shared service with one API shape, mountable on any resource:

- **Identity & roles.** One user record (Supabase `auth.users` + `user_profiles`), one `roles`/`role_members` model. A SCIM facade for IdP interoperability is an API-layer concern only. Every domain's "portal user," "resource," "agent," and "person handle" references this one identity — never a domain-local user table.
- **Lookups & reference data.** `lookup_types` → `lookup_codes` (effective-dated, sequenced, optional `set_id` partition), one LOV read endpoint (`GET /lookups?type=&set=`). Reference-data sharing by organizational determinant (business unit, cost org, project unit…) is one `set_assignments` table with a `determinant_type` column — not five parallel resources. Seeded ISO tables: currencies, languages, territories, time zones.
- **Custom fields.** A governed registry (`custom_field_defs`) over one `custom_fields jsonb` column per transactional table. This single decision deletes the thousands of flexfield child endpoints (DFF/EFF/GDF) that pollute every Oracle resource.
- **Translations.** One generic i18n table serving every translatable entity — no per-entity translation children.
- **Attachments & notes.** One polymorphic `attachments` table (Supabase Storage-backed) and one `notes` table, exposed by convention as `/{resource}/{id}/attachments` and `/notes`. Oracle mounts bespoke attachment trees on 40+ resources per family.
- **Background jobs.** One `job_requests` model (definition, typed params, recurrence schedule, priority, retries, status machine, result files) with one API: `POST /jobs`, `GET /jobs/{id}`, `POST /jobs/{id}/cancel` (`force` flag), hold/release. Every bulk import, mass action, plan run, document generation, and export in the suite is a job here. Never expose engine internals (Oracle publishes its scheduler's self-check-in endpoints).
- **Approvals & notifications.** One `workflow_tasks` inbox (typed back-reference to the source document — Oracle leaves it opaque), `POST /tasks/{id}/actions`, comments, history; one notifications feed. Every domain's submit-for-approval materializes here.
- **Audit.** Server-derived who-columns everywhere; append-only `audit_events` with per-object configuration; auth sign-in/out events included. Who-columns are never writable payload (Oracle accepts `CreatedBy` in create bodies).
- **Events & webhooks.** One event bus: per-domain topics, subscription management, webhook delivery. Oracle has at least three delivery idioms (polling feeds, per-job callbacks, per-product subscriptions); EBA has one, with Supabase Realtime for in-app live updates.
- **Search.** One platform search service (Postgres FTS + pgvector) used by knowledge, global search, and "find similar" features. Stateless `GET /search?q=` — never server-side search sessions with transaction bookkeeping.
- **Documents & templates.** One template + generated-document service (proposals, PO PDFs, program reports) running as jobs, results in Storage.
- **Data tables / rules payloads.** Where domains need admin-defined decision tables (CPQ data tables, matrix pricing), one `data_tables` + `data_table_rows` model with a single API surface — Oracle CPQ has three surfaces for the same rows.

**Supabase spine tables:** `user_profiles`, `roles`, `role_members`, `lookup_types`, `lookup_codes`, `value_sets`, `value_set_values`, `reference_sets`, `set_assignments`, `translations`, `custom_field_defs`, `attachments`, `notes`, `job_requests`, `workflow_tasks`, `notifications`, `audit_events`, `event_subscriptions`, `data_tables`, `data_table_rows`, plus seeded ISO reference. Also suite-wide conventions established here: `status_transitions` metadata (allowed next states per state machine) and the provenance triple (`source_system`, `source_document`, `source_line`) carried by every fact row that originates elsewhere.

### 5.2 Parties — one master for every person and organization

Oracle's deepest good idea, buried under its worst duplication: one underlying party table (TCA) exposed as accounts, contacts, households, hub organizations/persons, partners, competitors, suppliers, banks, resources — each a separate API with ~80% overlapping children, plus ~15 read-only projections (bill-to, ship-to, covered-party variants) shipped as separate collections. EBA builds the party model **once, suite-wide**, and every domain references it.

**In-app:** create and manage organizations, persons, and groups; addresses with purposes, contact points, relationships (person↔org employment/contact roles, householding), classifications, identifiers; role grants that make a party a customer account, contact, supplier, partner, competitor, or internal resource; duplicate detection, merge/link workflows with survivorship; team ownership and territory-driven assignment; source-system cross-references for integration identity.

**Supabase:** `parties` (unique `party_number`, `party_type` person/org/group), `party_person_profiles`, `party_org_profiles`, `party_addresses` (purposes as array, `is_primary` flag), `party_contact_points`, `party_relationships` (effective-dated), `party_roles` (the projection table: customer/contact/supplier/partner/competitor/resource usages), `party_classifications`, `party_identifiers`, `party_source_refs`, `party_merge_requests`, `sales_team_members` (polymorphic). Supplier- and customer-specific operational data (sites, BU assignments, credit profiles) live in their owning domains but FK here.

**API:** `GET/POST/PATCH/DELETE /parties/{partyNumber}` with `?type=` and `?role=` filters replacing every projection resource; children `/addresses`, `/contact-points`, `/relationships`, `/classifications`, `/team`; `POST /parties/duplicate-checks`; `POST /party-merge-requests`; `POST /parties/{pn}/assignments/run`. A bill-to view is a filter and a permission — never a second resource.

### 5.3 Products & catalog — one item master, one selling catalog, one configurator model

Oracle's item master (~300 operational attributes, org-scoped row clones, 12+ read-only LOV variants) lives in SCM PLM; CPQ maintains a *second* product world (product families/lines/models, parts, BOM item setups) synced from it. EBA has **one item master** with per-context layers.

**In-app:** create and govern items with revisions (effective-dated), org-level attribute overlays (not per-org clones), catalogs → category hierarchies → item assignments, item classes/statuses/templates, typed item relationships (GTIN, cross-reference, substitute, manufacturer part), structures/BOMs with components, substitutes, reference designators and multi-level explosion; engineering change orders with redlines, approvals, and affected objects; new-item requests; quality records (issues, actions, CAPAs, problem reports — one skeleton, typed); bulk import as jobs. For selling: a catalog layer (product groups/selling hierarchy), configurable model definitions with attributes, option domains, constraint/recommendation rules, and BOM mapping — the configurator's design-time model, versioned and published without parallel draft/deployed resource trees (`?state=` view instead).

**Supabase:** `items` (bkey `item_number`; typed core attributes + grouped jsonb for long-tail operational attributes), `item_org_settings` (per-org overlay), `item_revisions`, `catalogs`, `categories` (self-FK), `item_categories`, `item_classes`, `item_statuses`, `item_templates`, `item_relationships` (typed), `manufacturers`, `trading_partner_items`, `item_structures`, `structure_components` (+substitutes, reference designators), `change_orders` (+lines with redline payloads, participants), `quality_records` (typed), `product_models`, `model_attributes`, `attribute_options` (images/prices/translations embedded, not child tables), `configuration_rules` (jsonb conditions), `bom_items` (self-FK tree + mappings). Selling prices do NOT live here — pricing owns them (5.4).

**API:** `/items` (one list — filter params replace ~15 LOV variants), `/items/{itemNumber}` with `/revisions`, `/org-attributes/{org}`, `/categories`, `/relationships`, `/structures/{name}/components` (`?explode=true` for multilevel), `/catalogs`, `/change-orders` (+ `POST /{id}/status`), `/quality-records`, `/product-models` (+attributes/options/rules, `POST /{key}/publish` as a job), `/bom-items` (+`/tree`, `POST /{key}/generate-configurator` as a job), `POST /item-imports` (job).

### 5.4 Pricing — one engine, priced everything

Oracle runs at least three pricing stacks — SCM Pricing (price lists, discount lists, strategies, matrices, price books), CPQ Pricing Setup (charge definitions, price models, rate plans, agreements, matrices, rate cards), and subscription pricing — bridged by literal `syncWithFusionPricing` actions. EBA builds **one pricing service** consumed by quoting, ordering, subscriptions, and billing alike.

**In-app:** define charge vocabulary (one-time / recurring / usage charge definitions); price lists with item charges, tiered and block pricing, matrix rules; discount lists and rules; customer price agreements (contract pricing, effective-dated, with access control); rate plans and rate cards for subscription/usage pricing; pricing strategies with dimensional assignment rules; price books as published snapshots; currency conversion handling. Execute pricing as a stateless document-in/document-out engine returning the full price waterfall — callable from any domain and from outside.

**Supabase:** `charge_definitions` (code-keyed), `price_lists`, `price_list_items`, `price_list_charges` (tiers/blocks as jsonb), `discount_lists`, `discount_rules`, `price_agreements` (+items/charges), `rate_plans`, `rate_cards`, `pricing_matrices` (+columns; rows tabular for lookup), `pricing_strategies`, `pricing_strategy_assignments`, `price_books`, `price_book_lines`. Effective dating is pervasive and mandatory here.

**API:** CRUD on all setup resources with one casing and one method scheme (Oracle CPQ uses PUT on parts, PATCH on pricing, POST-deletes on rules — pick PATCH and stay there); `POST /price-calculations` — the stateless engine (absorbs both Oracle engines' RPC dialects); `POST /price-books/{number}/generate` and `/publish` as jobs. Money is one representation suite-wide (numeric amount + currency code columns; `{value, currency}` objects on the wire).

### 5.5 Configure, price, quote (CPQ)

Oracle CPQ is a separate product with its own dialect — to the point that quote endpoints are *composed from tenant metadata* (`commerce{Stage}{ProcessVarName}{MainDocVarName}/…`), action names are tenant-customized (`submit_t`, `cleanSave_t_bmClone_1_c`), and field names encode schema level by suffix (`totalContractValue_t`, `listAmount_l`). EBA builds quoting natively on the shared party, item, and pricing services — no sync actions, no second product world.

**In-app:** create quotes (typed by a configurable quote process, as a *field*, never a URL fragment); edit with live evaluate-without-saving (rules and pricing recalculated as the seller types — a genuinely good CPQ idea worth keeping); add lines from catalog, favorites, carts, or a configuration session; guided configuration sessions with constraint/hiding/recommendation rules, valid-domain feedback, BOM output, and save/resume drafts; price with full waterfall; approval workflow (submit/approve/reject/revise), versioning, copy, archive, lock; proposal document generation, email, e-signature; customer self-service carts and checkout; asset-based ordering — installed-base assets with modify/renew/suspend/resume/terminate lifecycle where `modify` projects the asset's future state into a new configuration session feeding a change quote; product recommendations.

**Supabase:** `quote_processes` (quote-type config incl. tenant attribute schema), `quotes` (optimistic-lock version, approval status, parent for revisions/copies), `quote_lines` (self-FK for BOM hierarchy, config snapshot jsonb), `quote_line_charges` (waterfall detail), `quote_approvals`, `quote_documents`, `quote_signature_requests`, `quote_events`, `configuration_sessions` (DB rows, not server cache), `carts` + `cart_items`, `favorites` + folders + share grants, `assets` + `asset_charges` + `asset_actions` log. Tenant-defined quote fields live in `custom_fields jsonb` described by the quote process — never in field-name suffixes.

**API:** `/quotes` CRUD + `POST /quotes/{id}/evaluate` (apply deltas, run rules, return computed state — no commit), `/price`, `/transitions` (one verb grammar: submit|approve|reject|revise|accept|publish|cancel), `/versions`, `/copy`, `/lines` (+`/charges`, `/rate-plans`), `/documents`, `/emails`, `/signature-requests`, `/orders` (handoff — better: an event the order domain consumes); `/configuration-sessions` CRUD with **GET** for derived results (recommendations, mandatory items, BOM, options — Oracle models these cacheable reads as POST actions); `/assets` + `POST /asset-actions` (one endpoint absorbing Oracle's ten: five verbs × instance and collection); `/carts`, `/favorites`. Concurrency via ETag/If-Match, replacing `revisionId`-in-body.

### 5.6 Sales force automation

**In-app:** leads with products, sources, scoring, and rules-driven assignment; qualification as plain status/rank fields (Oracle dresses single-field writes as accept/reject/rank verbs); conversion to opportunity or partner deal registration returning new ids; opportunities with revenue lines as the forecasting atom — each line carrying product, amount, close date, credit splits, recurrence, and territory alignment; stage history; win-probability; competitor/contact/campaign links; quote creation handing off to 5.5; territories defined by dimensional rules, explicitly versioned (Oracle keys territories by version id — proof versioning is required; model it properly); assignment engine invoked per object; forecasts territory-anchored with PATCH-to-adjust periods; quotas, goals, contests, KPIs; lightweight campaigns; partner management (profiles, programs, enrollments, deal registrations with approval, MDF budgets → fund requests → claims → settlements); activities (tasks/appointments/calls, one object) with templates and AI summaries; conversations and interaction timelines.

**Supabase:** `leads` (+products, conversions), `opportunities` (bkey `opty_number`), `opportunity_lines` (+`line_splits`, `line_territories` as real tables — forecasting joins on them), `opportunity_stage_history` (append-only), `territories` + `territory_versions` + rules/boundaries/values, `forecasts` + `forecast_items` + `forecast_adjustments` (audited), `quotas`, `goals`, `contests`, `partners` (party-backed), `partner_programs` + enrollments, `deals`, `mdf_budgets` → `mdf_fund_requests` → `mdf_claims` → `mdf_claim_settlements`, `activities` + assignees + polymorphic links, `assessments` (template-driven, polymorphic), `campaigns`.

**API:** `/leads/{leadNumber}` (real business key — Oracle uses an opaque hash), `POST /leads/{n}/conversions` (one endpoint, target field: opportunity|deal — absorbs three Oracle actions), `/opportunities/{optyNumber}` + `/lines` (+splits/recurrences/territories), `/territories` (+`/versions`), `/forecasts` (GET/PATCH), `/partners`, `/deals` + `/approval-actions`, `/mdf-budgets`→`/fund-requests`→`/claims`→`/settlements` (flattened top-level with FK filters), `/activities/{activityNumber}`, `/campaigns`. **Warning labels:** Oracle's ~2,130 smartActions endpoints (per-record UI action-bar bindings tripling the apparent API) never appear in EBA — UI affordances are app config; the ~15 read-only party projections and the MDM "hub" dialect are filters on `/parties`; published dead endpoints, ADF entity names (`OpportunityCompetitor2`, `MklProdAssoc1`), and the shipped typo resource (`/timeUnitOfMesaures`) are the cautionary tale for contract review before publishing.

### 5.7 Subscriptions & contracts

Oracle ships a full subscription-billing engine inside CX Sales, and enterprise contracts beside it; CPQ separately maintains price agreements it syncs with contracts. In EBA: **one contracts domain** (commercial agreements, terms, e-sign, lifecycle) and **one subscriptions domain** (recurring/usage billing) — both first-class, both on the shared pricing service.

**In-app — subscriptions:** subscriptions with products/charges (tiers, milestone events), bill lines with adjustments, covered levels (asset/party/site coverage, recursive), coverage terms and entitlement plans; lifecycle as one transition grammar (activate, amend, renew, suspend/resume, hold/unhold, close, cancel, withdraw, preview, duplicate) — Oracle exposes 17 actions duplicated at header and product level, 34 endpoints for one state machine; usage-based billing: usage event types, events, batches (submit/lock/revert/reverse), and a balance engine (codes, profiles, registers with periods/allowances/commitments — one ledger, not four parallel child trees); early-termination and credit calculations.

**In-app — contracts:** contracts with lines, parties/contacts, bill plans and revenue plans, terms sections/clauses from a clause library, documents and e-signature envelopes, status/approval history; lifecycle transitions (submit, sign, amend, revert, hold, close, reopen, cancel, new-version) with `validate` and `preview` as separate calls; AI key-term extraction and summaries; contract requests intake. Grants/awards from projects (5.14) are evaluated against this same agreement model — sponsor-side funded agreements, not a separate silo.

**Supabase:** `subscriptions` (bkey number) → `subscription_products` (PUID-style public keys — an Oracle pattern worth keeping) → `subscription_charges` → tiers; `bill_lines` + adjustments; `covered_levels` (self-FK); `subscription_transitions` (append-only lifecycle log; current status denormalized); usage tables + `balance_entries` (one table, `entry_type`); `entitlement_plans`, `standard_coverages`; `contracts` (bkey `contract_number` + explicit `contract_versions`), `contract_lines`, `contract_parties`, `bill_plans`, `revenue_plans`, `contract_terms_sections` → `contract_clauses`, `esign_envelopes`, `contract_status_history`, `contract_key_terms`.

**API:** `/subscriptions/{number}` with products/charges/bill-lines children; `POST /subscriptions/{n}/transitions` (one endpoint, action + effective date + reason); `/usage-event-batches` + transitions; `/balance-registers`; `/contracts/{contractNumber}?version=` (replacing composite-hash keys); `POST /contracts/{n}/transitions`; `/contracts/{n}/terms`, `/documents`, `/e-sign-envelopes`, `/key-term-extractions`, `/summaries`; `/entitlement-plans`, `/standard-coverages`. Entitlement checks (`GET /entitlements?asset=&sr=`) serve the service domain.

### 5.8 Orders & fulfillment

The heart of order-to-cash. Oracle's Order Hub duplicates the entire order tree three times (sync CRUD, async intake mirror, mass-action surface — the async mirror alone re-declares every child resource with different key names) and mixes four URL dialects in one collection. EBA: **one order aggregate**, with an async job envelope for high-volume intake and mass actions.

**In-app:** capture and revise sales orders with a deep but *sane* tree — lines with charges, payments, sales credits, manual price adjustments, lot/serial detail, project attribution, typed references (subscription, asset, coverage, drop-ship PO, transfer order); draft → submit → fulfillment tracking per line (schedule/promise/actual dates, reserved/shipped/invoiced status); holds applied/released at header or line; line split, substitution, scheduling updates as plain PATCHes; returns as order lines with return reason and original-order reference; create-customer-during-order-entry bridging to the party master; order promising — check availability, explore alternate fulfillment options with pegging, schedule/reschedule/cancel lines against global supply (one request schema with mode, absorbing Oracle's nine promising RPCs); channel revenue management — rebate/trade programs, accruals, and customer claims/deductions with settlement.

**Supabase:** `sales_orders` (bkey `order_number`; `source_system` + `source_order_ref` unique for external identity), `order_lines` (FK item, fulfillment org; `line_type` incl. return; FK original line), `order_charges` + `order_charge_components` (pricing output), `order_holds`, `order_payments`, `order_sales_credits`, `order_line_references` (one polymorphic typed table — Oracle has 12 child resources), `channel_programs` + rules + `channel_accruals`, `claims` + settlement lines. Fulfillment state lives on the line; the fulfillment chain (reservation → pick → shipment) belongs to 5.9 with FKs back.

**API:** `/orders` CRUD (`POST /orders` with async job wrapper for bulk intake — not a mirrored second tree); `/orders/{orderNumber}/lines` (+children); `POST /orders/{n}/submit`, `/cancel`; `POST /orders/{n}/holds`, `DELETE /holds/{id}`; `POST /orders/{n}/lines/{id}/split`; `POST /order-actions` (mass, as a job); `POST /order-promises:check|schedule|cancel`; `/channel-programs`, `/claims` + `/settle`/`/cancel`/`/reopen`. Order events (submitted, shipped, invoiced) publish on the event bus for billing, assets, and subscriptions to consume.

### 5.9 Inventory & logistics

**API highlights:** `/service-requests/{srNumber}` + `/queue-assignments/run`; `/activities` + `/transitions`, `/move`, `POST /activities/bulk`; `/field-resources/{id}/routes/{date}` + `/activate`; `GET /capacity`, `POST /booking-options`; `GET /activities/nearby`, `POST /field-resources/match`; `/articles` + `/checkout|checkin`, `/versions`, `POST /articles/{id}/publish {scope}`, `/translations`, `/ratings`; `GET /search?q=`, `POST /search/similar`, `POST /search/events`; `/conversations` + `/messages` (Realtime-backed), `/engagements` for the consumer leg.

### 5.17 The cross-domain flows — where the suite proves it is one product

Plan these as first-class deliverables, each exercised end-to-end in the stage where its last segment lands:

1. **Lead-to-quote-to-order:** lead → opportunity (revenue lines) → quote (configuration, pricing waterfall, approval, proposal, e-sign) → order — one party record, one item master, one pricing engine throughout.
2. **Order-to-cash:** order submit → promising/scheduling → reservation → pick → ship confirm → AR invoice (event-driven, not file-interfaced) → receipt → **writable cash application** → ledger posting. Returns ride the same rails in reverse.
3. **Procure-to-pay:** requisition (funds check) → PO (approval, acknowledgment) → receipt → AP invoice (2/3/4-way match) → validation → payment run → ledger. Change orders as versions; supplier portal as RLS.
4. **Source-to-contract:** negotiation → responses → scoring → award → generated POs/agreements → agreement pricing flowing back into requisition sourcing defaults.
5. **Plan-to-produce:** plan run → recommendations → released work orders/requisitions/transfer orders → production transactions → cost accounting → ledger.
6. **Hire-to-pay:** requisition → application pipeline → offer accept → hire (worker + relationship + assignment) → payroll-ready record → payroll flows → costing to ledger. One person identity from candidate to employee.
7. **Issue-to-resolution:** service request → entitlement check (subscription/coverage) → field activity (booking, dispatch, transitions) → debrief → billing; knowledge deflection measured via search events.
8. **Asset-to-renewal:** fulfilled order → installed-base asset → meters/warranty/maintenance → modify/renew projection → change quote → new order — the loop that ties CPQ, orders, service, and subscriptions together.
9. **Project-to-invoice:** project (chargeable tasks) ← costs from time/expenses/AP/inventory (provenance triple) → bill transactions → project invoice → AR → revenue.

## 6. EBA's API surface and the standing documentation requirement

- EBA's REST API is a first-class product surface, versioned once for the whole suite (`/api/v1/...`), designed to the constitution in Section 4.
- **Documentation is part of every build increment, not an afterthought.** As you build each stage, produce and maintain EBA's own API documentation — **Postman collections preferred**: one collection per domain, folders per resource, every operation represented with method, example request body, and example response, plus a single environment file containing only placeholder variables (base URL, credentials). Regenerate or update collections in the same change that alters an endpoint; drift between docs and API is a build failure.
- Keep the collections free of instance-specific values: no real hostnames, tenants, ids, or credentials — placeholders only.
- Alongside Postman collections, maintain a brief per-domain README covering the resource model and state machines — the things a collection cannot express.

## 7. Quality bars

- Every table in Supabase has row-level security policies matching the resource's authorization rules; the API never bypasses them.
- Every operation in the Postman collections runs green against a seeded demo database.
- Every state machine (order status, invoice status, application stage, …) is enforced in one place and documented.
- Cross-domain flows are tested end-to-end per stage: at minimum quote → order → shipment → invoice → payment, requisition → PO → receipt → AP invoice, and hire → assignment → payroll-ready record, once their stages exist.
- The three layers stay congruent: a schema migration, its API change, and its documentation update ship together.
